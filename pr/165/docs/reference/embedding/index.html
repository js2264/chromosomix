Embedding and driving chromosomix

Written from the app

This page is generated from chromosomix’s own code each time the documentation is built, so it is exactly what this version accepts. The same text is served to AI agents, as Markdown, from chromosomix.app/llms.txt.

An iframe

Section titled “An iframe”
  • The src is a link to a view, as the links page writes one, with ?embed=1 before the #. Or ?embed=1&config=<URL> for a saved workspace — several tabs, their tracks, colours and marks.
  • The frame is the view alone: no header, no tab strip, no status bar. The Annotations and Aesthetics panels are there, folded, because they are controls over the picture; the Files, General and Analysis panels are not. Add &panels=open to the query to open them both (panels=annotations or panels=aesthetics for one). A reader can still drop a file of their own on it.
  • The view fills the frame and follows its size, so a frame the reader can resize is a box away: see A frame the reader can resize, below.
  • For a figure that must not change, pin a release: https://chromosomix.app/v/<tag>/?embed=1#…. The root is the newest build, and changes with it.
  • Nothing is needed of the page around it — no Cross-Origin-Opener-Policy, no Cross-Origin-Embedder-Policy — and nothing of the data host beyond what any link needs: the frame’s requests come from the viewer’s origin, so a bucket whose CORS admits the viewer admits every page that embeds it.
  • An embed writes nothing to the reader’s storage and adds nothing to their back button: it shows what its src says, every time it loads.

The channel

Section titled “The channel”

Six messages, each an object with a type. Protocol version 1; a message is added without changing the number, so a host reads which messages a frame takes from its ready.

Message Direction Fields What it is
chromosomix:ready frame → page protocol, version, commit, accepts Sent once, when the frame is listening. accepts lists the messages it takes. It carries nothing about what is on screen.
chromosomix:where page → frame — Where is the view? Answered with chromosomix:state.
chromosomix:navigate page → frame state Go here. state is a patch laid over the view on screen: any key a link carries, so { locus: "IV:1,000,001-1,100,000" } moves a 1D browser and { transform: "log2", oe: true } re-colours a map. A key given null is removed; state: null is the landing page. Answered with chromosomix:state, saying where the view actually went.
chromosomix:add page → frame files Put these addresses in the tab, in order, as the app’s + does: a track among the tracks, a map or a 3D model beside the map; on an empty tab the first is its file. http(s) only, at most 64. Waits for the first picture, and is answered with chromosomix:state once every file is in. Builds before 0.17.0 do not take it.
chromosomix:state frame → page state The view: an object of the keys a link carries (uri, view, region, locus…), or null for the landing page. Sent in answer, and on every move once the page has spoken.
chromosomix:rendered frame → page report A picture is finished: report.status is drawn, gated (waiting for the reader to agree to a large read) or error, with report.maps (each map’s title, binsize, resolution, rows, cols), report.lanes and report.state, the view as a hash string. What to take a screenshot on.
  • The page speaks first. The frame answers only the window that framed it, and only once that window has sent it something; chromosomix:ready is the one message it sends unasked. Listen before the frame loads — put the script ahead of the <iframe>, or set its src from the script — so as not to miss it.
  • Replies go to the origin the page spoke from, never to *: the reader may open their own file in the frame, and only the page that asked is told.
  • Messages are carried out in the order they came. A navigate sent after an add waits for the files to open, and is laid over the view they opened.
  • A patch is read as a link is: a key the frame does not know is dropped, a value it cannot read is ignored. Read the answer to know where the view went.

In a Jupyter notebook

Section titled “In a Jupyter notebook”

The same frame as an anywidget, in JupyterLab, Notebook 7, VS Code, Colab and marimo. A file is an address or a path on the kernel’s disk, which the kernel serves to the frame by byte range from 127.0.0.1, sidecars and all; nothing is uploaded.

viewer="0.17.0" pins the build in the frame to a release; chromosomix.install_viewer() fetches one to serve beside the data, which is what makes local files work behind JupyterHub and offline.

In R: R Markdown, Quarto and Shiny

Section titled “In R: R Markdown, Quarto and Shiny”

In Shiny, chromosomixOutput(), renderChromosomix() and chromosomixProxy() drive a view on screen, and input$<id>_state follows the reader. A page knitted for others names its files by address: a local file is served only while the R session that rendered the page runs.

Both widgets are documented in the repository: Python, R.
